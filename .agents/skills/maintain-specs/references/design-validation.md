# テストと依存契約を満たす設計

要件から設計を作るときは、実装後の検査だけに頼らず、合格条件とそれを満たす責務・境界を先に定める。規模に合わせて既存設計へ追記し、同じ規則を複数の正本へ転記しない。

## 設計前の確認

- 対象要件とD-01、変更対象の採用設計をSpecServiceで取得する。対応するExample/Property Test仕様と既存テストを確認する。
- [機械測定の説明](../../../../tools/architecture/README.md)、[依存契約](../../../../tools/architecture/contracts.ini)、CIの合否条件を確認する。ツールの実行方法と版は説明を参照する。
- アーキテクチャを変更するときは、変更前の静的解析を実行する。出力先は上書きされるため、比較用JSONと元出力を別のwork配下へ退避する。過去の初回値を現状値として使わない。
- 現在通過している契約、既存不適合、今回改善する対象を分ける。ツールの警告と要件違反の確定を区別する。

## 設計に含める対応

対象ごとに次を記録する。小さな変更なら一つの表や段落でよい。

| 項目 | 記録すること |
| --- | --- |
| 要件 | 条件・期待結果・失敗時の保証・対象ID |
| 責務 | 規則を持つ部品、状態の所有者、生成・共有・更新・破棄のタイミング |
| 公開契約 | 入力・結果・失敗、値の所有権、外部副作用、呼出し側が知る必要のある情報 |
| 依存方向 | 許可する依存と禁止する依存、連携の担当 |
| 振る舞いの検証 | 代表例・境界・失敗・不変条件を検証する既存または追加テスト |
| 構造の検証 | 適用するImport Linter契約、内部アクセス・循環・複雑度などの確認対象と合格条件 |
| 性能 | 性能に影響する場合、同一データ・操作・計測区間による比較方法 |

同じ理由で変わる状態・規則・処理をまとめ、利用側がその内部属性やファイル配置を操作しなくて済む契約にする。新しい責務境界は、可能なら禁止依存・独立性・レイヤーの契約として実装前または実装と同時に追加する。契約が既存不適合に接続する場合は、影響する経路と今回の解消範囲を明記する。

## 実装と検証

1. 既存テストを再利用し、変更する契約や保証に不足する回帰テストを追加する。実装と同じ分岐を写すテストより、公開契約の結果・不変条件を検証する。
2. 実装後に対象テスト、適用契約、静的解析を実行する。必要な範囲の統合・UI・性能検証を加える。データ隔離はSAFE-001に従う。
3. 変更前後の依存辺・警告位置・対象関数の複雑度を比較する。総件数の減少だけで、新しい循環や内部構造への依存を見逃さない。今回導入した依存契約違反は構造を修正して解消する。
4. テストを通す目的だけで、検査の除外、ルール無効化、しきい値緩和、基準値の更新を行わない。要件・契約自体の変更が妥当なら、理由と影響を設計に記録して検証仕様とともに更新する。
5. 設計を採用したことと、実装が検証を通過したことを分けて報告する。未実行・不適合・手動確認待ちは、そのまま対応表へ残す。

既存コード全体の未解消警告は、今回の局所変更だけで解消済みとしない。凝集性の意味は静的解析だけでは確定しないため、機械検査の結果を責務・変更理由に照らして判断する。必要な実操作ができない場合は、その確認を保留とし、独立して進められる設計・合成検証を続ける。
